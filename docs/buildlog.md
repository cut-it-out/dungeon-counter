# dungeon-counter — Build Log

Running record of how this project was built with Claude Code. "I" is the developer; Claude Code is named in the third person.

## Part 1 — Decisions locked so far

- Agent behavior: Claude Code makes surgical edits only, runs tests right after every change, prefers explicit code over abstractions, asks instead of guessing when requirements are unclear, and presents 2-3 options with trade-offs before writing code when several patterns are valid. The rules are in CLAUDE.md under "Agent Behavior" (directed, Session 1).
- Build log: `docs/buildlog.md` in the attributed voice. It is read at the start of every session and written at the end, as stated in CLAUDE.md (directed, Session 1).
- Game: a five-minute potion-stall shop-management challenge for a fictional client (Pocket Lantern Games): predictable customer rushes, two competing upgrades, net profit as the goal with a personal best. It replaced the idle sim after my playtest review (directed, Session 6). Brief in `docs/BRIEF_dungeon-counter-idle-sim.md`, palette in `docs/dungeon-counter-brand-palette.md`. The spec is `docs/GDD-dungeon-counter-v3.md` until v4 is written after the pivot code; v1 and v2 are kept for provenance (directed, Session 2). The second upgrade track deviates from the brief's "one upgrade track"; the case study states it (Session 6).
- Stack & hosting: Phaser + Vite + TypeScript, Vitest for the economy; mobile portrait 390×844; Cloudflare Pages via Git integration; GitHub `cut-it-out/dungeon-counter` (proposed → accepted, Session 2).
- Economy: one product; deterministic customer arrivals at a calm interval with predictable rush windows; fixed-batch restock with a cooldown after each restock; two competing upgrades, Better Brews (+price per level) and Bigger Crates (+potions per crate at the same crate cost); 300 s of game time that pauses when hidden; pure TypeScript module driven by both Phaser and the headless runner (directed, Session 2; rushes, cooldown and Crates directed, Session 6).
- Score: net profit = closing balance − `startCoins`, with a personal best per config; an upgrade bought late is a loss. Replaces GDD v3 §12.1's gross revenue (directed, Session 6).
- Baseline: the challenge loop gets a new frozen baseline, `challenge-v1`, proposed by Claude Code without simulation; tuning goes in a separate revised config. The idle sim is preserved as a git tag (`idle-loop-v1`) with its `baseline-v1` played runs as the before-evidence; `baseline-v1` numbers stay frozen. Provenance for `baseline-v1` = this log's Session 2 + the unmodified v1 GDD in commit `94bf7af` (directed, Sessions 2 and 6).
- Dead-shop guard: an upgrade is blocked when even selling the whole shelf at the new price could not fund a restock: `coins − cost + stock × priceAt(level + 1) < restockCost` (same as the old rule at stock 0). Reason text "Need 53c to stay stocked" shows the unlock amount (directed, Session 4; GDD v3 §15).
- Play policy: my evidence runs on the challenge configs are free play. The headless runner plays scripted strategies (all-Brews, all-Crates, mixed) as the dominance check: if one always wins, the choice is fake (proposed → accepted, Session 6). The fixed policy (restock at stock ≤ 1, otherwise upgrade, restock first) applied to the idle-loop runs (Session 4).
- Execution plan: `docs/PLAN-dungeon-counter-v1.md` (S1–S18 + S5a), approved (directed, Session 3); S1–S5a done (Session 4); S6–S9 done (Session 5); S11 Cloudflare Pages connected by me before S10 (Session 5). The challenge pivot is inserted before S12, and S10 moves to the new build (directed, Session 6); the plan text is updated after the pivot code.
- Event log, save and CSV: every row carries `run_id` (`run-` + 4 hex), `run_type`, `config_id`; `session_start` / `resume` rows carry full state with amount 0; save key `dungeon-counter-save:v1:<configId>` holding state in integer ms plus all rows, written after every event, on pause, hide and `pagehide`; "✓ Saved" / "Not saved" follows the write result; New day confirms whenever a saved log would be replaced (title and summary); CSV is `\n`-separated with `elapsed_s` to one decimal; download by default, share sheet only on touch devices that can share files (Claude's call, Session 5).
- Config selection: `?config=baseline|revised`; default baseline until `REVISED_ACCEPTED` in `src/config/index.ts` is flipped together with the acceptance note in `balancing/notes.md`; unknown values fall back with a title notice (Claude's call on the mechanism, Session 5).
- Customer motion: each customer walks in from the left, reaches the counter exactly at its arrival time, scales up ~15% and back for a sale (no scale-up on a missed sale), then walks out right; position is a pure function of game time in `src/scenes/customer.ts`, so pause/resume need no tweens (directed, Session 5; details Claude's call).
- UI rendering: Phaser draws only the shop scene, a 390×400 design-px canvas FIT-scaled in the middle of a CSS flex column; HUD, buttons, reason text, menus and summary are an HTML overlay (proposed → accepted, Session 3; canvas size Claude's call, Session 4).
- Stack versions: Phaser 3.90.0 (plan says 3.x), TypeScript 7.0.2, Vite 8.3.4, Vitest 5.0.5 with `silent: false`; `npm test` / `npm run dev` / `npm run build` (Claude's call, Session 4).
- Assets: Kenney CC0 sprites (Roguelike/RPG Pack + Roguelike Characters), picked by Claude Code for my review; unused candidates stay in `public/assets/candidates/` until clean-up; every file credited in `CREDITS.md` (directed, Session 4).
- Evidence: ≥1 (target 2) played runs per config (free play on the challenge configs, Session 6); CSV with `run_id`/`run_type`; one SQL aggregation via DuckDB, run with `uv run --with duckdb balancing/run_sql.py` (directed, Session 3); idle time, action spacing, first-upgrade time, revenue/minute, surplus, missed sales as metrics; medals P2; simulator CLI P2 (directed, Session 2).
- Time box: ~3 days (18–24 h), one day over the brief; stated in the case study (directed, Session 2).
